# Fixture: m0-basic

A single, fully synthetic call used to exercise VoiceWire's M0 evidence
pipeline end-to-end.

## Contents

- `call.pcap` -- a synthetic SIP/RTP capture (10 packets: INVITE, 200 OK,
  ACK, 5 RTP packets, BYE, 200 OK).
- `agent-trace.json` -- a synthetic agent trace using VoiceWire's tiny M0
  trace-fixture JSON format (not a standard; see
  `../../docs/evidence-model.md`).
- `capture-context.json` -- a manifest explicitly declaring the PCAP's
  capture vantage point (VoiceWire never infers this from packet contents).
- `expected-report.json` -- the `report.json` produced by running
  `voicewire analyze` against this fixture, checked in as a regression
  baseline.
- `generate_fixture.py` -- the script that generated `call.pcap`.

## How it was generated

`call.pcap` was generated by `generate_fixture.py` using `scapy` to
hand-assemble raw Ethernet/IP/UDP frames containing literal SIP text and a
manually packed RTP header. All addresses (`127.0.0.1`), ports, the
Call-ID (`voicewire-m0@example.test`), and packet timestamps (starting at a
fixed synthetic epoch, `2026-01-01T00:00:00Z`) are fixed and synthetic.
Re-running the script regenerates the file deterministically.

**`scapy` is a fixture-authoring tool only.** It is not a VoiceWire runtime
dependency and does not appear in `pyproject.toml`. VoiceWire itself never
parses or constructs SIP/RTP packets -- that is TShark's job, exercised here
by running the real `tshark` binary against `call.pcap`.

`agent-trace.json` and `capture-context.json` were written by hand to match
`call.pcap`'s Call-ID and timing.

## Contains no customer/production data

Every value in this fixture -- addresses, ports, Call-ID, timestamps, SDP,
RTP payload bytes (constant `0xFF` filler, not real audio) -- is synthetic
and was authored for this repository. Nothing here originated from a real
call, a real customer, or a real deployment.

## Capture vantage point

Declared explicitly in `capture-context.json`:

- `vantage_point.kind`: `agent_host`
- `vantage_point.label`: `voice-agent-01`
- `interface`: `eth0`
- `supplied_by.method`: `fixture_manifest`

This is asserted metadata, not something extracted from the packets. A real
PCAP captured without an accompanying manifest describing where it was taken
from should be analyzed with capture context left `unspecified`.

## Codec / media assumptions

RTP packets declare payload type 0 (G.711 PCMU) with a 20ms packetization
interval (160 samples at 8kHz per packet). No audio is actually encoded --
the RTP payload bytes are constant filler. M0 does not decode or inspect
media content in any way; the codec/timing fields only exist so TShark's RTP
dissector has realistic-looking header values to extract.

## Clock assumptions

This fixture deliberately uses **exact, aligned clocks**: `agent-trace.json`
declares `clock.alignment_to_capture_clock.type = "exact"`, meaning the trace
clock (`fixture-clock`) and the PCAP's capture clock
(`pcap.capture_clock`) are asserted to be the same wall clock, because both
were authored against the same fixed synthetic epoch. This is a deliberate
fixture property used to demonstrate the "exact alignment" path through the
architecture -- it is not something VoiceWire assumes about arbitrary
real-world inputs. Real captures should either supply a genuine alignment
(exact or an explicit, justified offset) or be analyzed with the alignment
left `unresolved`.

**This is a fact about clocks, not about capture location.** This fixture's
clock alignment is declared in `agent-trace.json`'s own `clock` section; its
capture vantage point is declared separately in `capture-context.json`. Both
happen to be known here only because the fixture generator controlled both
inputs -- one is never inferred from the other, and
`tests/test_capture_context_clock_independence.py` proves that running the
same PCAP/trace pair with each declaration present or absent, independently,
produces the corresponding independent result.

## What M0 proves (with this fixture)

- The PCAP and trace are independently hashed and registered as artifacts.
- TShark extracts real SIP evidence (Call-ID, method/status, CSeq) and real
  RTP evidence (SSRC, sequence number, payload type, RTP timestamp) from an
  actual capture, with frame-number provenance.
- The trace adapter ingests a source-defined event type
  (`first_audio`) without strengthening it into a more specific claim the
  source never made.
- The trace's declared SIP Call-ID is correlated to matching SIP evidence via
  exact string match, with the correlation citing the exact SIP evidence IDs
  that support it.
- The SDP media negotiated in the INVITE/200 OK (address, port, payload
  type) is correlated to the observed RTP stream by exact endpoint match --
  `sip:call_id:voicewire-m0@example.test` ↔ `rtp:stream:0xcafebabe` -- citing
  both SDP-carrying SIP evidence and every RTP packet in the stream. No SDP
  port mapping is guessed; the match requires the RTP stream's address,
  port, *and* payload type to equal what the SDP literally declared.
- Clock domains and their declared alignment are represented explicitly in
  the output, and that alignment's own provenance (`declared_by`) is
  distinct from the capture context's provenance (`supplied_by`) -- neither
  is inferred from the other.
- `report.json` is deterministic evidence/reconstruction output: rerunning
  `voicewire analyze` against this fixture on the same VoiceWire version
  reproduces the same evidence, IDs, and correlations (excluding
  environment-reported `runtime.python_version` / `runtime.tshark_version`,
  which legitimately vary by machine).

## What M0 explicitly does NOT prove

- Nothing about call quality, latency, or where time was spent. There is no
  diagnosis in this report -- see `scope_note` in `report.json`.
- Nothing beyond exact-match SDP/RTP endpoint correlation. M0 does not
  reconstruct SIP dialog *state* (early/confirmed/terminated), does not
  handle multiple `m=` lines per SDP body, and does not resolve media
  direction (send/recv/sendrecv) -- it only proves that a specific,
  literal (address, port, payload type) triple appears in both an SDP
  declaration and an observed RTP stream.
- Nothing about audio actually heard by a caller. "Audio observable at a
  capture point" is not the same claim as "audio heard by the caller," and
  this fixture (with no vocoded audio at all) cannot demonstrate that
  distinction either way.
- Nothing about what would happen with clocks that are *not* exactly
  aligned -- see the dedicated clock-alignment unit tests for that behavior
  instead of this fixture.
